# Postmaker

A static HTML5 page that generates a bilingual (Hindi + Urdu) social-media
post image and lets the user download it as a PNG.

## What it does
- User fills in text (Hindi Title / Body / Signature, Urdu Title / Body /
  Signature), picks a Hindi font and an Urdu font, sets per-element font
  size / bold / italic, picks a **layout**, and chooses a Dark or Light theme.
- "Generate Image" renders the selected layout to **1080 × 1350 PNG(s)** via
  html2canvas, shows them on the page, and offers per-image + "Download all".
- All inputs are persisted to **localStorage** (`postmaker.state.v1`) on every
  change and restored on reload.

## Layouts (pluggable)
- Three selectable layouts (radio in the form, persisted as `state.layout`):
  - **Side by side** (`sideBySide`) — Hindi left / Urdu right, body is one row
    per line (paired by index), single page, capacity-limited with a warning.
  - **One pair at a page** (`onePair`) — one couplet per page: 2 Hindi lines
    then 2 Urdu lines, centered with one common width + justified. Titles &
    signatures hug the centre (Hindi right, Urdu left). Paginated 2 lines/lang
    per page; each page shows "n of N" bottom-centre; prev/next buttons in the
    preview move between pages; **Generate** captures every page, Download all
    downloads them.
  - **Stack** (`stack`) — title & signature use the same two-cell
    `buildPairTable()` structure as `sideBySide`, but **hug the centre** (Hindi
    right-aligned, Urdu left-aligned, as in `onePair`) so they sit over the
    body instead of out at the half-column centres. The body is **not** paired
    by index: the whole Hindi body prints first, then the whole Urdu body, each
    line full width and centred on one common width + justified (as `onePair`
    does). Single page, capacity-limited with a warning.
    `planRows()` builds the print order. **This layout inserts no rhythm of
    its own** — unlike `sideBySide`/`onePair` there is no empty row after every
    two lines; the body prints exactly as typed. It therefore uses its own
    `typedLines()` rather than the shared `splitLines()`: blank lines are
    **kept** (they become empty rows, so the user's own spacing is what shows)
    instead of dropped, with trailing blanks trimmed since those are a stray
    Enter at the end of the textarea. The one automatic blank is the separator
    between the Hindi and Urdu blocks, which is structural. Row height is
    **per language**
    (`fontRowHeight({hindi:true,urdu:false}, …)` and the mirror), so a tall
    Nastaliq block doesn't force the Hindi rows to match it; `bodyCapacity()`
    is therefore *not* usable here — `fitRows()` accumulates the per-row
    heights instead and pops any spacer left dangling by truncation.
- Each layout is a **separate file**: `js/layouts/<id>.js` registers
  `window.LAYOUTS[id] = { id, name, pageCount(), renderPage(page) }`, and
  `style/layouts/<id>.css` holds its styling (scoped by `.layout-<id>` on
  `#mainFrame`). `app.js` builds the empty `#mainFrame`, applies frame chrome
  (theme/layout class, top margin, background), and calls the layout to build
  the page. Shared builders in `app.js`: `buildPairTable("Title"|"Signature")`,
  `buildFooter()`, `frameInnerHeight()`, `makeLineDiv()`, `measureTextWidth()`,
  `bodyCapacity()`, `splitLines()`, `urduText()`, `lineStyleFor()`.

## Inputs & formatting
- The Hindi and Urdu control groups sit in collapsible native `<details>`
  sections (`.lang-section` / `.lang-summary`) so the settings below them stay
  reachable without scrolling (no Bootstrap JS is loaded).
- The six text inputs and their formatting controls are **generated by
  `app.js`** from the `ELEMENTS` config (key, label, default text, default
  fmt). Each element's `key` matches its layout cell id (e.g. `hindiTitle`).
- Each element has: a text box, a font-size number input, and Bold / Italic
  toggle buttons. These are applied to the layout cell as inline
  `font-size` / `font-weight` / `font-style`. Two extra boxes sit between Size
  and the B/I buttons: **Urdu Signature has a `Width` box** (see the signature
  width-matching note below) and **both bodies have a `Height` box** (see the
  body row height note). Both default to blank = `auto`.
- **All Text Size** (`#allSizeInput` + Apply, `applyAllSizes()`) writes one size
  into every element's size input in one go; the individual inputs stay
  editable afterwards. It's a setter, not persisted itself (the per-element
  sizes are).
- Default size is **36px everywhere**; nothing is bold by default.
  Nothing is italic by default (the old CSS forced signatures italic — that was
  removed).
- Default text: Hindi Signature `वक़्क़ास 'सिफ़र'`, Urdu Signature
  `وَقَّاص  صِفر`; Title defaults to the 1st option (Hindi `ग़ज़ल` / Urdu
  `غزل`); bodies blank.
- **Titles are linked comboboxes** (`TITLE_OPTIONS` in `app.js`): each title
  input has a `datalist` of predefined options (ग़ज़ल/نظم … etc.). Hindi and
  Urdu options are counterparts by index — picking the nth option in one
  language auto-fills the nth option in the other (`syncTitle()`). Free-text is
  allowed and does not sync the counterpart.
- Default fonts: Hindi → Eczar, Urdu → Noto Nastaliq Urdu.
- **Kasheeda** (`#kasheedaInput`, off by default): when on, `addKasheeda()`
  inserts the tatweel char (U+0640) at every valid join in **all Urdu text**
  (titles/body/signature, at render time only — the input value is untouched).
  Rule: a kasheeda goes after a left-joining letter and before a right-joining
  one; `NON_CONNECTORS` (alif/dal/re/waw/yeh-barree families + hamza) take none
  after them, and diacritics stay attached to their base. Persisted in state.
- **Space width — IMPORTANT.** The Urdu fonts ship an effectively zero-width
  space glyph. Measured advances: Jameel Khushkhati 0.003em, Jameel Noori
  Nastaleeq 0.006em, Mehr Nastaliq 0.024em, Urdu Khush Khati 0.030em, Noto
  Nastaliq Urdu 0.132em — against Eczar 0.265em and Kurale 0.309em. Typed
  spaces therefore all but vanish and typing *more* of them does nothing
  visible (a space in Jameel Khushkhati is ~0.1px at 36px). `applyTextStyle()`
  fixes this by topping every space up to `MIN_SPACE_EM` (0.25em) via
  `word-spacing`: `extraWordSpacing()` = `size * MIN_SPACE_EM -
  measureSpaceWidth()`, clamped at 0, so the Hindi fonts (already wider) get
  `0px` and are unaffected. `measureSpaceWidth()` must set the measurer to
  `white-space: pre` — the shared measurer's `nowrap` collapses the run.
  Verified against html2canvas 1.4.1: `word-spacing` is honoured in the capture
  (the word gap in the PNG grew 19px → 63px for a 5-space signature).
  **Titles and the Hindi signature only** — body lines and the Urdu signature
  are justified to a fixed width instead, so their spacing is set by
  justification and runs of spaces collapse there (`white-space: normal`);
  applying word-spacing to body lines would also desync `measureTextWidth()`
  from the rendered width.
- **The Urdu signature line has a settable width.** A `Width` number box sits
  next to its Size box (`#urduSignatureWidth`, generated by `buildInputs()` —
  it is the only element that gets one, keyed off `el.key === "urduSignature"`,
  so `controls[key].width` is `null` for every other element; guard with
  `if (c.width)`). Blank (the default, shown as the `auto` placeholder) means
  **match the Hindi signature**; a number sets the line width in px directly.
  Either way the span is justified to fill that width, so the pair lines up
  (`urduSignatureWidth(both)` + `justifyToWidth()`, applied in
  `buildPairTable()` for `kind === "Signature"`). Persisted as
  `state.elements.urduSignature.width` (`null` = auto). The Hindi side is never
  touched. An explicit width is clamped to the cell (`bodyColWidth()` — 430px
  beside Hindi, 870px when Urdu is alone) and applies **even when Hindi is
  off**, whereas auto needs a Hindi signature to measure and so returns 0 then.
  A width smaller than the text's natural width is honoured and will wrap the
  signature onto a second line — that's the user's own number, left visible
  rather than silently ignored.
  **The body lines deliberately have no such box** — a `Width` control was
  added for them and then reverted at the user's request; body width stays
  automatic (the measured longest line). Body *height* is settable though —
  that is a separate control, see below. Consequence:
  typing extra spaces in the **Urdu signature** no longer widens it — the
  width is pinned and justification redistributes the gaps evenly. The Hindi
  signature and both titles keep the `word-spacing` behaviour above.
  `urduSignatureWidth()` returns 0 (leave it alone) when the Urdu signature has
  no space to stretch, or is naturally *wider* than the Hindi one —
  justification can only stretch, never compress, so forcing it would wrap it
  onto a second line. The target is capped at `bodyColWidth(2)` (430px) so a
  very long Hindi signature can't push the Urdu one out of its cell; if the
  Hindi signature is long enough to wrap, the two boxes no longer match
  exactly (a single-line stretch can't match a wrapped box).
  `measureStyledWidth()` does the measuring and must mirror how each span
  actually renders — `pre` for the Hindi cell (still `pre-wrap`, so typed runs
  of spaces count) and `nowrap` for the Urdu one (switched to `normal`, so runs
  collapse) — and it folds in the `word-spacing` top-up, which plain
  `measureTextWidth()` does not.

## Layout
- Based on `layout.html` (kept for reference), borders removed.
- `#mainFrame` is the capture target, hard-clamped to 1080 × 1350
  (`max-width`/`max-height` + `overflow: hidden`), `position: relative`.
- **The preview is scaled to fit the screen — IMPORTANT.** 1080px is wider than
  a phone (and wider than the Bootstrap column on most monitors), so
  `applyPreviewScale()` shrinks `#mainFrame` to its wrapper with a `scale()`
  transform (`transform-origin: top left`, set in `style.css`), recomputed on
  `resize`. **It must stay a transform.** A transform doesn't change the layout
  box, so `offsetWidth`/`offsetHeight`/`clientHeight` — and therefore
  `measureTextWidth()`, `frameInnerHeight()`, `bodyCapacity()`, `fitRows()` —
  still see the true 1080 × 1350 and the page lays out identically on a phone
  and a monitor. Don't "simplify" this to `zoom`, or to shrinking the frame's
  `width`/`height`: either changes the layout box and the preview would stop
  matching the exported PNG. Nothing in the codebase may use
  `getBoundingClientRect()` for layout maths for the same reason (it *is*
  scaled); `offset*` only.
  The transform is dropped for the whole capture via the same `capturing` flag
  that hides the debug outlines — html2canvas 1.4.1 **does** honour transforms,
  so leaving it on would export a shrunken, offset image. Verified: the PNG is
  1080 × 1350 and byte-identical (same SHA-256 of the data URI) whether
  generated at a 375px or a 641px viewport.
  `.frame-wrapper` is `overflow: hidden`, **not** `auto`: the browser builds the
  scroll area from the frame's *untransformed* border box, so `scrollWidth`
  stays 1080 + padding however far the preview is scaled down, and `auto` put
  scrollbars on both axes around a preview that already fitted. Nothing is
  clipped — the frame is anchored top-left and scaled to fit. `app.js` also
  pins the wrapper's height to the scaled height, since the untransformed
  layout box would otherwise reserve all 1350px and leave a large gap.
- Page margin is 100px (`.mainFrame` padding). The **top margin is adjustable**
  via the Top Margin input (`#topMarginInput`); `applyTopMargin()` sets
  `padding-top` and the body-fit calc uses `getTopMargin()`. Persisted in state.
- **Background image** (optional): a file input (`#bgImageInput`, + Clear) reads
  the chosen image as a **data URI** (kept in the `backgroundImage` var so it
  persists and never taints the export). `applyBackground()` draws it on
  `#mainFrame` (`background-origin: border-box`, so the reference box is the full
  1080×1350). A **display-mode** select (`#bgModeInput`, `backgroundMode`) maps to
  CSS: fill=`cover`, fit=`contain`, stretch=`100% 100%`, center=`auto`, tile=
  `auto`+`repeat`; shrink & scaleDown use natural size if it fits else `contain`
  (needs the image's natural size — `loadBgNaturalSize()` loads it and re-renders).
  Persisted in state, but `saveState()` drops the image and retries if it blows
  the localStorage quota.
- **Body rows must NOT clip (`overflow: visible`) — IMPORTANT.** Nastaliq
  descenders reach well below the row box: Noto Nastaliq Urdu at 60px overshoots
  its row by ~15px, so `overflow: hidden` on the row/body containers sliced the
  tails off the text. All six of those rules were removed —
  `.bodyArea`/`.bodyLines td` (sideBySide), `.onePairBody`/`.centerRow`
  (onePair), `.stackBody`/`.stackRow` (stack). Glyphs now paint into the
  neighbouring row, which is intended: overlapping is better than losing the
  text. **`.mainFrame` keeps its `overflow: hidden`** — that's the real guard,
  hard-clamping the capture to 1080×1350, so nothing escapes the image.
  Verified in the html2canvas capture, not just the preview (it honours
  `overflow: visible`): descenders gained 14px in sideBySide and 20px in
  onePair/stack. Don't reintroduce `overflow: hidden` on a row to "keep things
  tidy" — it silently eats glyphs. Side effect to know about: a body line too
  wide for its column wraps inside its row div, and that second visual line used
  to be clipped away invisibly; it is now drawn, overlapping the next row.
- **No flexbox in the captured frame** — html2canvas 1.4.1 mangles flex, so the
  layouts use normal flow + tables (which it renders reliably). Both layouts
  share the vertical rhythm: title (top) → `BODY_GAP` (60px) → body → `BODY_GAP`
  → signature (flows up after the body) → footer logo, **absolutely positioned**
  bottom-right so it stays fixed while the signature floats up.
- Two columns: `.hindiCell` (left, LTR) / `.urduCell` (right, RTL), 20px gap
  (10px padding each inner edge). Title/signature are 1-row `.lineTable`s built
  by `buildPairTable()`. **Centering title/signature in their cell is the
  shared default in `style.css`** (`.titleCell, .signatureCell { text-align:
  center }`); it wins over `.hindiCell`/`.urduCell` on source order (equal
  specificity), so keep it after them. `sideBySide` takes the default and
  declares nothing. `onePair` and `stack` both override it to hug the centre
  with `.layout-<id> .titleCell.hindiCell` (0,3,0 beats the default's 0,1,0,
  so file order doesn't matter). `applyTextStyle()` sets font size/family/weight/style
  **and line-height (= size × `LINE_FACTOR`, so Nastaliq isn't squeezed)** inline
  on the span. Alignment is layout-specific (see the layout CSS).
- **Language toggles**: `Hindi`/`Urdu` checkboxes (`#hindiEnabled` /
  `#urduEnabled`, both on by default). Cells are built only for enabled
  languages (`getEnabled()`); a single language spans full width. At least one
  must stay on (`onToggleLang`). Persisted in state.
- **Debug outlines** (`#debugBordersInput`, off by default): adds
  `.debug-borders` to `#mainFrame`, which colour-codes a 1px **outline** on
  every box inside the frame (table red / tr orange / td green / div blue /
  span pink / img cyan, legend in `#debugLegend`). `outline` — not `border` —
  so it occupies no space and the preview geometry stays identical to the
  export. **Preview only**: `generateImage()` sets the `capturing` flag, which
  makes `applyFrameChrome()` drop the class for the whole capture loop and
  restore it afterwards. (html2canvas 1.4.1 ignores `outline` anyway — captures
  with and without the class are byte-identical — so this is belt and braces.)
  Persisted in state.

### Body line mechanics (shared)
- Body is **not** a flowing paragraph — it's one visual line per input line.
  Helpers in `app.js`, used by the layout modules:
  - `splitLines()` drops blank lines; Urdu lines get `urduText()` (kasheeda).
  - row height = `fontRowHeight()` — by default the **measured natural line
    height** of the chosen font at its size (via `measureTextHeight()`, a
    hidden span with line-height normal), so switching to a tall font
    (Nastaliq) grows the rows and a short font shrinks them. Title/signature
    line-height is measured the same way in `applyTextStyle()`. Each input line
    is one deterministic row.
  - **`Height` box (both bodies) overrides that row height.** Blank (the
    default, shown as the `auto` placeholder) keeps the measured behaviour
    above. `pinnedRowHeight()` reads the box (null for blank/0/junk, clamped to
    `OUTPUT_HEIGHT`) and `langRowHeight()` picks pinned-or-measured per
    language; **`fontRowHeight()` is the single place this plugs in**, so all
    three layouts pick it up with no change to the layout modules. Where a row
    holds both languages (`sideBySide`, `onePair`) it can only have one height
    so the taller of the two wins; `stack` calls `fontRowHeight()` once per
    language and so honours each block's own value independently. Persisted as
    `state.elements.<body>.height` (`null` = auto). Because row height feeds
    `bodyCapacity()`/`fitRows()`, pinning a tall row legitimately reduces how
    many lines fit and `#bodyWarning` updates to match (200px rows took a
    10-line body down to 3 lines shown).
  - `measureTextWidth()` finds the longest line; all lines are set to that width
    and justified (`text-align`/`text-align-last: justify`) to fill it. In
    *side-by-side* with both languages, the two columns share one common width.
    **`text-align-last` is the load-bearing half**: each div holds a single
    line, which is therefore also its own *last* line, and plain `text-align:
    justify` never stretches a last line. The Urdu signature reuses this via
    `justifyToWidth()`.
  - *Side-by-side* caps the line count to what fits (`bodyCapacity()` over the
    measured available height, accounting for the spacer after every two lines)
    and shows `#bodyWarning` if the text overflows the single page.
  - *One pair at a page* takes a fixed 2 Hindi + 2 Urdu lines per page and
    paginates instead of warning.
  - *Stack* fits rows of mixed (per-language) height with its own `fitRows()`
    and warns like side-by-side; `total` there is Hindi + Urdu lines (they
    stack), not `max()` of the two (they pair), and counts only non-blank rows
    — a typed blank line is spacing, not a "line" the warning should mention.
- Footer logo: Dark theme → white logo, Light theme → black logo. The PNGs
  live in `assets/img/`, but are **embedded as base64 data URIs** in
  `js/logos.js` (`LOGO_DATA_URI`) and `applyTheme()` sets `logoImg.src` to those.
  This is required: an image loaded from `file://` (or any other origin) taints
  the canvas and makes `toDataURL()`/download throw a SecurityError. Data URIs
  keep the canvas clean, so the app exports correctly even when opened from disk.
  **If you change the logo PNGs, regenerate `js/logos.js`.**

## Themes
- Dark: bg `#0A0A0A`, text `#FAFAFA`.
- Light: bg `#FAFAFA`, text `#333333`.
- Applied via the `.theme-dark` / `.theme-light` classes on `.mainFrame`.

## Fonts — IMPORTANT
- Requirements said `./fonts/hindi` and `./fonts/urdu`, but the actual files
  live under **`./assets/fonts/hindi`** and **`./assets/fonts/urdu`**.
- A browser cannot list a directory, so the available fonts are hard-coded in
  `js/fonts.js` (`FONT_MANIFEST`). **Add new fonts by editing that manifest** —
  the dropdowns are built from it automatically.
- Fonts are registered with the `FontFace` API and we `await document.fonts.ready`
  before calling html2canvas so the capture uses the real font, not a fallback.

## File structure
- `index.html` — markup (current folder, per requirements)
- `style/style.css` — shared styles; `style/layouts/*.css` — per-layout styles
- `js/fonts.js` — font manifest + loader
- `js/logos.js` — base64 logo data URIs (`LOGO_DATA_URI`)
- `js/layouts/*.js` — one file per layout (registers into `window.LAYOUTS`):
  `side-by-side.js`, `one-pair.js`, `stack.js`. Adding a layout = new
  `js/layouts/<id>.js` + `style/layouts/<id>.css` + a radio in `index.html`
  and the two `<link>`/`<script>` tags; `app.js` needs no change.
- `js/app.js` — UI wiring, shared builders, paging, PNG generation
- `assets/img/` — logo PNGs (source for `logos.js`); `assets/fonts/` — fonts
- `lib/` — empty; only used if a library must be self-hosted

## Gotchas
- html2canvas needs fonts and the logo image loaded before capture (handled in
  `generateImage()` — `await document.fonts.ready` + wait for `logoImg`).
- **Works from `file://`** (open `index.html` directly) — the logos are inlined
  as data URIs so the canvas isn't tainted, and fonts load from same-origin
  relative paths. A local web server also works but isn't required.
- **Serve the project over HTTP when testing changes.** Node (`C:\Program
  Files\nodejs`) and Python (`C:\Python314`) *are* installed — an earlier note
  here claiming otherwise was wrong. `.claude/launch.json` defines a
  `postmaker` config (`python -m http.server 8777`). Opening `index.html` over
  `file://` works for real use, but browsers cache `file://` subresources hard:
  edits to `js/app.js` / `style/*.css` repeatedly kept serving the **old**
  file, which looks exactly like "my change did nothing". Over
  `http://localhost:8777` every reload is fresh.
- html2canvas 1.4.1 mishandles flexbox — the captured `#mainFrame` deliberately
  uses normal flow + tables, not flex. Don't reintroduce flex inside the frame.
- `text-align: justify` is suppressed by `white-space: pre-wrap`/`nowrap`; body
  line divs use `white-space: normal` so justification works.
